## P0-2：update_issue 不验证 assigned_agent_id 有效性

**文件**: `backend/app/api/issues.py` 第 155-169 行  
**问题**:
```python
for field, value in body.model_dump(exclude_unset=True).items():
    if value is not None:
        setattr(issue, field, value)  # 直接写入，无验证
```
如果传入不存在的 `assigned_agent_id`，SQLite 不强制 FK 检查，会写入无效值。后续派发时查不到 Agent 会崩溃。

**修复方案**:
```python
if "assigned_agent_id" in body.model_dump(exclude_unset=True):
    agent_id = body.assigned_agent_id
    if agent_id is not None:
        result = await db.execute(select(Agent).where(Agent.id == uuid.UUID(agent_id)))
        if not result.scalar_one_or_none():
            raise HTTPException(400, f"Agent {agent_id} 不存在")
```

**工作量**: 约 10 行，低风险

## P0-3：fetchTaskTree 响应解析错误，永远返回 []

**文件**: `frontend/src/api/issues.ts` 第 163-166 行  
**根因**: 前端期望后端直接返回数组，但后端返回的是 `{ "issue_id": "...", "nodes": [...] }` 对象。

**后端实际返回**（`get_issue_task_tree` 端点）:
```json
{
  "issue_id": "xxx",
  "nodes": [
    { "id": "n1", "name": "...", "status": "pending", ... }
  ],
  "from_db": true
}
```

**前端错误代码**:
```typescript
export async function fetchTaskTree(issueId: string): Promise<TaskTreeNode[]> {
  const res = await get<TaskTreeNode[]>(`/issues/${issueId}/task-tree`);
  return Array.isArray(res) ? res : [];  // res 是对象，不是数组 → 永远返回 []
}
```

**修复方案**:
```typescript
export async function fetchTaskTree(issueId: string): Promise<TaskTreeNode[]> {
  const res = await get<any>(`/issues/${issueId}/task-tree`);
  return Array.isArray(res?.nodes) ? res.nodes : [];
}
```

**工作量**: 约 3 行，低风险

## P0-4：decomposeIssue 响应解析错误，Issue 状态损坏

**文件**: `frontend/src/api/issues.ts` 第 135-141 行  
**根因**: 前端期望后端返回 Issue 对象，但后端返回的是 `{ "ok": true, "issue": {...}, "task_tree": {...} }` 包裹对象。

**后端实际返回**（`decompose_issue` 端点）:
```json
{
  "ok": true,
  "issue": { "id": "...", "title": "...", ... },
  "task_tree": { "nodes": [...], ... }
}
```

**前端错误代码**:
```typescript
export async function decomposeIssue(issueId, strategy): Promise<Issue> {
  const res = await post<Issue>(`/issues/${issueId}/compose`, { strategy });
  return normalize(res);  // res 是 { ok, issue, task_tree }，normalize 后 Issue 字段全部 undefined
}
```

`normalize(res)` 将整个响应对象当作 Issue 处理，`issue_id` 变成 `res.issue_id`（不存在，因为真实 ID 在 `res.issue.id`），导致返回的对象所有字段均为 `undefined`。

**修复方案**:
```typescript
export async function decomposeIssue(
  issueId: string,
  strategy: DecompositionStrategy = 'hybrid',
): Promise<{ issue: Issue; taskTree: any }> {
  const res = await post<any>(`/issues/${issueId}/compose`, { strategy });
  return {
    issue: normalize(res.issue),
    taskTree: res.task_tree,
  };
}
```

**工作量**: 约 10 行（需同步修改调用方），低风险

## P0-5：updateIssue 用原始 fetch() 无 Auth header

**文件**: `frontend/src/api/issues.ts` 第 119-127 行  
**问题**:
```typescript
export async function updateIssue(issueId: string, data: {...}): Promise<Issue> {
  const res = await fetch(`/api/v1/issues/${issueId}`, {  // ← 原始 fetch
    method: 'PATCH',
    headers: { 'Content-Type': 'application/json' },  // ← 无 Authorization
    body: JSON.stringify(data),
  });
  ...
}
```
项目中 `http.ts` 已提供统一 HTTP 方法（自动注入 Auth header），但 `updateIssue` 未使用。

**修复方案**:
```typescript
export async function updateIssue(issueId: string, data: {...}): Promise<Issue> {
  const res = await http.patch<Issue>(`/issues/${issueId}`, data);
  return normalize(res);
}
```

**工作量**: 约 5 行，低风险

## P0-6：submit_task_with_workflow() 生成的 Workflow 不更新 Scheduler

**文件**: `backend/app/runtime/kernel.py` 第 310-347 行  
**根因**: `submit_task_with_workflow()` 先调用 `submit_task()` 入队（使用空的 `default_workflow: start→end`），然后生成真实 Workflow 保存到 `self._workflows[task_id]`，但 **从未更新 Scheduler 队列中已入队的 `ScheduledTask.workflow_spec`**。

**执行链路**:
```
submit_task_with_workflow()
    ├─ submit_task() → 入队 ScheduledTask(workflow_spec=default_workflow)
    └─ generate_workflow() → 保存到 self._workflows[task_id]
        ↓
Scheduler 执行时读取 ScheduledTask.workflow_spec
    = default_workflow (start→end，空操作)
    ↓
所有任务实际执行的是空工作流，Planner 生成的计划被丢弃
```

**修复方案**（详见《详细功能文档》）:

修改 `submit_task_with_workflow()` 执行顺序：
1. 先生成 Workflow（或至少先生成后再入队）
2. 或者：在 Scheduler 执行前检查 `kernel._workflows` 是否有更新

采用方案：**先生成 Workflow，再入队**。

修改 `submit_task` 支持传入 `workflow_spec` 参数；`submit_task_with_workflow` 先生成 workflow，再调用改造后的 `submit_task`。

**工作量**: 约 30 行，中等风险（涉及运行时核心路径）

## P0-7：_execute_llm() LLM 失败后静默吞异常

**文件**: `backend/app/runtime/execution_engine/node_executor.py` 第 206-211 行  
**问题**:
```python
except Exception as e:
    logger.exception("LLM call failed in node '%s'", node.id)
    state.setdefault("messages", []).append({
        "role": "system",
        "content": f"LLM call failed: {e}",
    })
    # ← 没有 raise，没有 increment error_count，没有设置 workflow_status
```
LLM 调用失败后，错误消息作为 `system` role 追加到 `messages`，工作流继续执行后续节点。后续节点如果依赖 LLM 输出，会收到错误字符串。

对比 Tool 节点失败处理（正确）:
```python
# Tool 节点
output_msg = f"Error: {result.error}"
state["error_count"] = state.get("error_count", 0) + 1
```

**修复方案**:
```python
except Exception as e:
    logger.exception("LLM call failed in node '%s'", node.id)
    state.setdefault("error_count", 0)
    state["error_count"] += 1
    state.setdefault("messages", []).append({
        "role": "system",
        "content": f"LLM call failed: {e}",
    })
    # 可选：达到最大错误数后设置 workflow_status
    max_errors = node.config.get("max_errors", 3)
    if state["error_count"] >= max_errors:
        state["workflow_status"] = "failed"
```
**工作量**: 约 15 行，低风险
